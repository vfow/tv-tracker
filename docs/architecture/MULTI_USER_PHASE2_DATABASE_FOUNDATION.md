# Multi-user Phase 2 database foundation

Status: Phase 2 is complete only after migration `0007_multi_user_database_foundation`, its regression coverage, normal exact-head CI, merge, production migration, restart, and health verification all succeed.

Phase 2 builds the database/account identity foundation locked in Phase 1. It does **not** replace the current singleton administrator login, create the owner's replacement account, expose account creation, send email, create server-side sessions, or assign existing tracker data to an account.

## Safety boundary

Public registration remains source-locked closed. The existing GET `/signup` route remains only the informational `Registration coming soon` surface. There is still no public signup POST/account-creation path.

The production database currently contains legacy globally-owned data. Migration 0007 deliberately adds nullable `user_id` columns and does not backfill them. Existing rows remain unassigned (`NULL`) until the controlled migration sequence reaches the owner-account migration step. This prevents Phase 2 from inventing an account identity or silently changing ownership.

No current primary key or global uniqueness constraint is removed in this phase. Full UUID-scoped query ownership and composite identity changes belong to the later isolation phase, after authentication can supply a trusted user UUID.

## Schema version 7

The current application schema version becomes 7. The v1-v6 migration SQL and checksums remain unchanged. `registry_v7.py` composes the historical v1-v6 registry into the current registry, removes the old latest-only schema contract from the historical migration objects, and attaches the current schema contract only to migration 0007.

This preserves the migration-ledger guarantee that already-applied migration checksums never change.

## `tv_tracker_users`

Migration 0007 creates `tv_tracker_users` with the Phase 1 identity/lifecycle foundation:

- `user_id UUID PRIMARY KEY`; UUIDs are generated by server-side application code, not supplied by clients.
- display/original `email` plus `email_normalized`.
- display/original `username` plus `username_normalized`.
- unique normalized email and username constraints.
- `password_hash` only; plaintext passwords are never stored.
- role constrained to `user` or `admin`, defaulting to `user`.
- status constrained to `unverified`, `active`, `deactivated`, or `pending_deletion`, defaulting to `unverified`.
- `email_verified_at`.
- `session_version` foundation for later security/session invalidation.
- `deletion_requested_at` and `deletion_due_at` foundation for the later 30-day deletion lifecycle.
- created/updated timestamps.
- database checks that normalized identifiers match their display values and usernames obey the locked 3-30 letter/number/underscore rule.

`tvtracker.auth.accounts` owns the initial account identity primitives: server UUID generation, role/status constants, identifier normalization, and username validation. Creating/authenticating accounts is intentionally deferred to later phases.

## Ownership scaffolding

A nullable UUID `user_id` column plus a user-first lookup index is added to every Phase 1 user-owned boundary:

- `tv_tracker_shows`
- `tv_tracker_history`
- `tv_tracker_state`
- `tv_tracker_meta`
- `tv_tracker_changes`
- `tv_tracker_notification_settings`
- `tv_tracker_notification_baseline`
- `tv_tracker_notification_events`
- `tv_tracker_notifications`
- `tv_tracker_final_notification_settings`
- `tv_tracker_movie_notification_baseline`
- `tv_tracker_push_subscriptions`
- `tv_tracker_push_presence`
- `tv_tracker_push_deliveries`
- `tv_tracker_security_events` (nullable account association for security/rate-limit events)

The columns are intentionally nullable and have no defaults. A migration or request cannot accidentally label legacy data as belonging to a fabricated user.

Foreign keys and replacement composite uniqueness/primary-key constraints are not introduced yet. They must be added only when the runtime query layer is UUID-aware and the transition rules for legacy unassigned rows are in place. This avoids breaking the currently deployed singleton-admin application while still making the future ownership boundary explicit in the schema.

## Schema certification

The v7 schema contract preserves the complete v6 table/column/constraint/index validation, allowing only the newly expected `user_id` columns on the historical relations. It additionally certifies:

- `tv_tracker_users` exists as an ordinary permanent table;
- all required account columns have the expected PostgreSQL types/nullability;
- all named account primary/unique/check constraints exist and are validated;
- each ownership scaffold column is a nullable UUID with no default/identity/generated value;
- each Phase 2 ownership lookup index exists;
- the pending-deletion lookup index exists.

Unledgered legacy schema versions 4, 5, and 6 remain adoptable through the existing fail-closed validation path. A real v6 database is stamped with its historical migration prefix, migration 0007 is applied transactionally, and only then is schema version 7 recorded.

## Phase 2 exit criteria

Phase 2 is complete when:

- current schema version is 7 and migration 0007 is the latest migration;
- historical v1-v6 SQL/checksums are unchanged;
- `tv_tracker_users` and all required constraints exist;
- every locked user-owned boundary has nullable UUID ownership scaffolding and an index;
- existing production tracker/notification/push rows remain unassigned and unchanged;
- no account is automatically created;
- public registration is still closed;
- the legacy singleton admin login/recovery path still works;
- exact-head CI passes, including PostgreSQL migration/regression tests;
- the merged production migration, application restart, and public health verification succeed.

Phase 3 starts from this schema and introduces account-bound authentication/server-authoritative sessions without opening public registration.
